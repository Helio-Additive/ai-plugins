# Language client choices

The [Helio code-generation guide](https://docs.helioadditive.com/en/developers/code-generation/) supplies the original TypeScript, Python, Rust and C++ examples. Ruby, Go, Java, Kotlin, Swift and C# are additional integration recipes grounded in their libraries' own documentation, not a claim that Helio publishes or operates official SDKs for those languages.

Selections reviewed on 2026-11-08:

- **Ruby — graphql-client:** schema validation and accessor generation during loading, with a small HTTP adapter. The [community repository](https://github.com/github-community-projects/graphql-client) is not archived; its latest commit observed during review was 2025-12-06. Its slower maintenance cadence warrants checking Ruby/GraphQL gem compatibility. No extra wrapper gem is needed, and no static Ruby codegen guarantee is claimed.
- **Go — genqlient 0.8.1:** generates operation functions and result structs with standard HTTP integration. [Configuration](https://github.com/Khan/genqlient/blob/v0.8.1/docs/genqlient.yaml) supports local SDL and nullable pointer handling. With Go 1.26, its old `x/tools` dependency failed compilation; the recipe explicitly updates to 0.52.0 and retains the generator as a Go tool dependency.
- **Java — DGS codegen 8.8.0 / client platform 12.1.0:** maintained schema-generated query builders and POJOs. [Codegen documentation](https://netflix.github.io/dgs/generating-code-from-schema/) explains the builder approach. The recipe uses the nondeprecated [DgsCustomGraphQLClient](https://github.com/Netflix/dgs-framework/blob/v12.1.0/graphql-dgs-client/src/main/kotlin/com/netflix/graphql/dgs/client/DgsCustomGraphQLClient.kt) with JDK HTTP. It avoids requiring Spring Boot, though the library still has transitive framework dependencies. Builders differ from operation-specific response generation.
- **Kotlin — Apollo Kotlin 5.2.0:** operation-specific Kotlin models and suspend execution; fits a concise JVM program without Android. The tagged [JVM setup](https://github.com/apollographql/apollo-kotlin/blob/v5.2.0/libraries/apollo-gradle-plugin/testProjects/jvm-library/build.gradle.kts) and [dependency catalog](https://github.com/apollographql/apollo-kotlin/blob/v5.2.0/gradle/libraries.toml) ground its plugin DSL and Kotlin version.
- **Swift — Apollo iOS 2.5.0:** SPM, a matching CLI and native async execution for Apple platforms. The [CLI guide](https://www.apollographql.com/docs/ios/code-generation/codegen-cli) and tagged [transport](https://github.com/apollographql/apollo-ios/blob/2.5.0/Sources/Apollo/RequestChain/RequestChainNetworkTransport.swift) ground the recipe. This has more setup than raw URLSession, but generates operation models and prevents manual request/response duplication.
- **C# — Strawberry Shake 16.7.3:** build-time typed client generation. Its [console guide](https://chillicream.com/docs/strawberryshake/get-started/console) uses the Server client package, which does not require hosting a server. The recipe uses a local schema configuration instead of CLI initialization that fetches a second schema.

These versioned examples are starting points, not perpetual compatibility promises. Recheck upstream releases when adopting, resolve and lock dependencies in the destination project, and keep codegen and runtime versions compatible. Do not add test targets, mocks or a new runtime service just to use these templates.

Validation during this change: Go and Swift generated and compiled against a
validated schema obtained through public introspection. Ruby snippets passed
syntax checks only. Java/Kotlin and C# were checked against upstream APIs but
were not compiled because the local machine lacks a working JDK and .NET SDK.
No authenticated probe or business operation was executed.
